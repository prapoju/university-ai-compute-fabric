- (decision) Paradigm: layered read-only intelligence layer over a deterministic evidence pipeline; hexagonal ports/adapters where every operational-state and policy access is a read-only port and the LLM is an outbound prose adapter; binds: all components; prevents: copilot becoming system of record or an executor.
- (decision) Stack (verified 2026-09): Python 3.11 + FastAPI 0.141 + uvicorn (single-process backend); React 19 + TypeScript + Vite 8 (three-pane console SPA); Ollama 0.34 local LLM runtime (offline per A-12); SQLite for Module-12-owned stores (audit, sessions, evidence, proposals). Simulated state = in-process dataclass providers seeded from fixture files; snapshot-able for determinism tests.
- (decision) Determinism mechanism (adopts PD-1 lean, OQ-5): retrieval-composition. Deterministic Evidence Assembler produces a fixed EvidenceSet; per-intent Diagnosers + Window Calculator are pure functions; factual claims are emitted as structured Claim objects (each with citation bindings) so FR-13 coverage is a data check; LLM invoked exactly once per answer to render connective prose only. No constrained decoding needed.
- (decision) Event-log design (adopts PD-2 lean, OQ-6): reason-on-event. The denial/cancellation/cordon event records its reason at creation; no policy-version replay. Binds event provider + retrospective diagnoser.
- (decision) Entity match tolerance (adopts PD-3 lean, OQ-9): exact id match in v1; typo tolerance deferred. Entity resolution is fully deterministic, never LLM-assisted.
- (decision) Re-dispatch semantics (adopts PD-6 lean): a re-dispatch is a NEW proposal requiring a fresh dry-run + confirmation gate; each dispatch is a separate proposal logged separately, preserving FR-10 exactly-once per confirmed proposal.
- (decision) No messaging infrastructure. All contracts are synchronous request/response HTTP; dry-run re-validation is pull-based re-query, not push events. No queue/event bus (violates proportionality).
- (decision) Safety state machine is server-side and ordered: refusal -> dry-run -> confirmed -> dispatched, persisted in the proposal store; confirmation is a distinct HTTP request, provider-independent; dispatch requires a stored confirmation referencing a validated non-empty dry-run snapshot. Adopts UX-01..UX-07, UX-26 resolutions.
- (decision) Read-only provider ports: users, catalog+access-policy, groups, jobs, nodes, reservations, policy-windows, events. Provider port surface is fixed to what registered intents require; adding a mutating or control-plane method is a PRD-scope change (D1, D2, C-4).
- (assumption) Headless run: defaulted to the bmad-architecture Fast path per the fully-specified activation payload; all inputs pre-supplied (PRD + Phase 2 UX artifacts + boundary + deliverable structure).
